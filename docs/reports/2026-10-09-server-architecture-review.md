# 翡翠街服务器架构成熟度审查报告

审查日期：2026 年 10 月 9 日。审查对象：当前工作区实现，包括未提交的新模块与配置；不能只用 Git 提交 `d59caef` 代表本次受审版本。

**结论：需要修改，当前尚不满足基本中型游戏的服务端成熟度。** 单权威进程、模块化服务、PostgreSQL、Socket.IO 和 Caddy 的组合适合这款经营游戏，可以继续使用。主要缺口是身份失效处理、事务边界、恢复日志和每条指令的全世界处理成本。问题需要修复，但不需要引入微服务或多副本集群。

本次整理了 **11 项问题：7 项 P1，4 项 P2**。其中 8 项属于已通过针对性执行确认的逻辑问题，1 项是实测容量缺口，1 项是持续集成配置问题，1 项是依赖公告与发布门槛问题。P1 表示影响身份、资产、全服权限或中型容量，应优先处理；P2 表示影响可靠性、运维或发布验收，需要在公开运营前补齐。

## 审查范围和判断标准

审查覆盖服务器启动与关闭、业务指令入口、账号与游客会话、交易与托管服务、定时结算、世界状态与持久化、实时同步、运行状态、部署、备份和发布测试。检查了市场、公盘、工坊、直播、黑市、矿区等模块的主要服务边界，并运行完整现有回归。

这里的“基本中型成熟度”指：能够长期运营，玩家身份有效，多人交易资产一致，已确认操作可恢复，故障不会产生成功假象，注册玩家积累后仍有可用容量，发布和恢复可以重复执行。用户尚未指定在线人数和每秒操作目标，因此报告不承诺某个具体在线人数；本机性能数据用于判断现有路径的增长趋势。

本次只新增审查报告，没有修改服务器实现、依赖、部署配置或用户存档。现有回归与补充测试使用隔离进程、内存世界或临时数据。当前环境没有 Docker 和 PostgreSQL 客户端／服务，真实 PostgreSQL、容器构建、生产主机、TLS 与异地恢复仍需在部署环境验收。

## 身份和生产权限问题

### R1 会话失效重新开放账号认领

**需要修改；存在实际身份绕过 bug。**

[player-session-service.js](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/player-session-service.js:106) 使用 `!hasSession(player)` 判断是否允许 `legacy-claim`。但是 `hasSession` 只判断当前有效会话，过期或全部撤销后的正规玩家也会进入旧存档认领分支。该分支没有校验提交的令牌，也没有排除已经绑定密码的账号。

玩家 ID 本身会出现在 [公开玩家状态](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/snapshot-service.js:135)，不能充当秘密。

复现结果：绑定密码的账号执行 `logout-all` 后，新 Socket 只提供该玩家 ID、不提供恢复令牌，仍收到相同玩家 ID 的 `hello` 和私有状态。独立服务测试也确认，所有会话过期后，错误令牌会获得新的 `legacy-claim` 令牌。

最小修改：用明确的一次性存档迁移标记区分真正的旧存档；会话过期、被撤销和已绑定账号均不能进入无凭据认领。生产旧存档认领应通过受控迁移或已有可信凭据完成。无需增加一套身份系统。

验收：过期、撤销、绑定账号三个场景中，仅提供公开 ID 必须拒绝；密码登录仍可恢复；旧存档迁移最多执行一次。

### R5 撤销会话后旧连接仍有操作权限

**需要修改；存在实际会话撤销 bug。**

[退出接口](/Users/jar/Documents/翡翠/jade-market-prototype/server/gateway/account-routes.js:142) 只删除会话与 Cookie，没有终止对应 Socket。游戏指令取玩家时依赖 socket 到 player 的映射，没有检查会话是否已经撤销。游客令牌与 Cookie 登录均有这个边界问题。

真实进程复现：`logout-all` 返回 200 后，原 Socket 仍成功执行 `setName`，客户端收到已修改的名字。攻击者已经建立的连接也不会因为“退出全部设备”失去权限。

最小修改：连接记录认证会话 ID；单会话退出在耐久提交后断开对应连接，全部退出断开玩家房间内全部连接；排队指令执行时检查其会话仍有效，防止撤销前排队、撤销后执行。这里不需要每条指令查询数据库。

验收：另一台设备执行全部退出后，旧连接无法改名、购买或扣款；新密码登录可以继续使用。

### R7 普通玩家自动成为生产数值审核员

**需要修改；存在生产权限边界 bug，除非明确把全服数值治理设计为玩家权利。**

[mining-service.js](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/mining-service.js:603) 在未配置 `JADE_MINING_TUNING_REVIEWER_IDS` 时，从 founder 或 competition 玩家中自动选择审核员。[权限判定](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/mining-service.js:496) 接受这个玩家；审核、撤销和回滚全服矿区租金／产出规则的 Socket 指令在生产同样注册。

生产环境示例没有配置该变量。默认配置下创建 50 名达到正常矿区条件的玩家，执行世界更新后，一名普通玩家的 `tuningGovernance.canManage` 为 `true`，`reviewerMode` 为 `founder`。正式版本生成还要满足观察样本条件，但管理身份已经错误授予。

最小修改：生产模式取消自动候补授权；未显式配置审核员时禁用正式数值写操作。审核名单可以继续使用现有配置，不需要新增复杂角色系统。开发模式可保留便捷行为。

验收：空生产审核名单时所有普通玩家均无法审核、撤销和回滚；只有显式指定账号可以执行这些操作。

## 持久化和并发问题

### R2 检查点保存了后来失败的操作

**需要修改；存在资产恢复不一致 bug。**

[指令协调器](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/durable-mutation-coordinator.js:45) 的指令队列和 [PostgreSQL 检查点队列](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/postgres-world-persist.js:444) 分开运行。检查点直接从 [当前可变世界](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/postgres-world-persist.js:382) 取快照，因此可以捕获指令修改后、耐久提交前的状态。数据库事务锁只能串行 SQL，不能保护取快照时的内存状态。

故障注入顺序：一个检查点正在等待数据库；第二个检查点已经排队；游戏指令将现金 100 改为 90，其增量保存排在第二个检查点后；检查点保存 90；随后指令保存失败并回滚。最终内存现金为 100，但从数据库检查点恢复后为 90。

相同边界也影响管理手动保存：先 `drain()` 再另行 `flush()` 不会阻止新指令插入。

最小修改：自动保存与手动保存都通过同一个世界调度边界安排，只在没有未提交世界变更时捕获检查点；检查点快照与对应日志游标保持同一提交边界。无需额外数据库、消息队列或多份热世界。

验收：检查点与扣款交错后强制扣款保存失败，再模拟重启；恢复结果必须与回滚后的世界一致，并检查投影和审计没有记录失败操作的成功结果。

### R3 数据库请求编号唯一范围错误

**需要修改；存在操作成功但恢复时丢失变更的 bug。**

内存去重按玩家保存 `processedRequestIds`；数据库增量日志却使用 [全局唯一的 request_id 和 action](/Users/jar/Documents/翡翠/jade-market-prototype/server/persistence/migrations/002_incremental_world_journal.sql:19)，审计表也使用 [相同范围](/Users/jar/Documents/翡翠/jade-market-prototype/server/persistence/migrations/001_world_snapshots.sql:75)。[写入逻辑](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/postgres-world-persist.js:349) 发生冲突时静默跳过日志插入，仍更新投影、提交并发送成功结果。

按实际唯一约束实现的适配器复现：两名玩家分别执行 `setName`，使用相同合法 requestId；两次操作都返回成功，日志只有一行。在下一个覆盖该操作的检查点之前重启，第二名玩家恢复为旧名字。交易使用相同路径，会产生同类恢复问题。

同一玩家的历史只有最近 200 条，而日志在几个检查点之间仍可能保留更早的键，因此只修复跨玩家索引范围还不够：已退出内存历史的旧编号再次出现时，也不能让日志跳过而内存继续变更。

最小修改：统一玩家、事件和请求编号的幂等范围与保留策略；为旧索引新增迁移，不改写已发布迁移；通过插入结果识别重复，禁止“没有追加日志但按新指令提交变更”。可返回确定的重复结果，不要求无限保留所有响应。

验收：跨玩家相同编号、同玩家连续重复、超过历史长度后重试三种场景，提交后世界和检查点加日志重放结果完全相同。

### R4 读状态和断线绕过指令提交边界

**需要修改；存在未提交状态外发和死连接恢复 bug。**

[requestState](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/socket-handlers.js:266) 直接读取可变世界，未进入指令协调器。指令等待数据库时，另一个请求的异步上下文没有事务，因此 Socket 包装不会替它延迟发送。

复现：扣款把现金从 100 改为 90，暂停保存；此时请求全状态，客户端立刻看到 90；随后保存失败，内存恢复为 100。断线回调也会直接广播当前世界，可能向其他玩家发出相同的未提交状态。

另外，[disconnect](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/socket-handlers.js:1006) 会立即删除绑定，但 [回滚](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/durable-mutation-coordinator.js:119) 恢复事务开始时全部 socket 绑定。复现中连接已经解绑，保存失败后该死连接又出现在世界映射里，在线数量仍为 1。这会影响离线结算判断和活跃资格。

最小修改：全状态读取和公开广播只读取已提交状态，或排在当前变更完成后；业务回滚与实时连接注册表分开处理，不复活已经断开的 Socket。连接清理保持及时，不能简单把网络断线延后到数据库保存结束。

验收：暂停保存并请求状态／断开另一连接，再注入保存失败；客户端只能看到已提交数据，断开玩家不再算在线，重连正确进入离线恢复路径。

### R6 HTTP 排队操作持有旧玩家引用

**需要修改；存在保存故障后的假成功 bug。**

[账号接口](/Users/jar/Documents/翡翠/jade-market-prototype/server/gateway/account-routes.js:112) 和 [管理接口](/Users/jar/Documents/翡翠/jade-market-prototype/server/gateway/admin-routes.js:72) 在排队前获取玩家对象，并由闭包保留。回滚的 [importSnapshot](/Users/jar/Documents/翡翠/jade-market-prototype/server/world-store.js:173) 会重新填充玩家 Map，旧对象已经不是权威玩家。

复现：第一条交易等待保存；管理操作先取得该玩家并排队；交易失败导致玩家对象替换；管理操作随后修改旧对象并成功返回。旧对象显示已封禁，权威世界里的玩家却没有封禁记录。账号绑定和撤销存在相同引用模式。

最小修改：排队时只保留玩家 ID、会话标识和请求值；在实际执行时重新获取玩家并验证身份／权限。无需引入统一对象代理或复杂仓库框架。

验收：交易回滚后排队的封禁、账号绑定、撤销会话均实际作用于世界中的当前玩家；不能只验证 HTTP 返回值。

## 容量和发布问题

### R8 每条指令仍处理完整世界

**需要修改；这是实测架构容量缺口。** 当前数据库保存的是差量，但生成差量的成本仍是全世界级别。

[协调器](/Users/jar/Documents/翡翠/jade-market-prototype/server/services/durable-mutation-coordinator.js:49) 在每条指令前后各调用一次世界导出；[世界导出](/Users/jar/Documents/翡翠/jade-market-prototype/server/world-store.js:141) 复制所有玩家、世界集合并执行完整校验；[差量生成](/Users/jar/Documents/翡翠/jade-market-prototype/server/persistence/world-delta.js:11) 再逐一序列化比较所有玩家。PostgreSQL 适配器还会再次复制传入的前后快照。

没有结算变化的到期任务 tick 也需要取得前置世界快照。广播虽然复用了公开快照，但 [逐连接发送](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/server-context.js:151) 仍重新生成个性化片段、比较签名。公开快照包含全部已保存玩家；一名玩家的公开指标变化，会导致整个 players 顶层数组成为补丁。

本机 Node 24.14.0 实测，使用真实 `makePlayer` 和订单初始化创建新手存档，预热后执行 5 次只改一个玩家名字的指令，取平均。测试在完整回归结束后单独运行；不包含数据库、网络、广播，也不包含 PostgreSQL 适配器的额外复制。

| 已保存玩家数 | 完整快照体积 | 每条改名指令平均耗时 | 按平均耗时折算的串行处理率 |
| --- | --- | --- | --- |
| 100 | 1.67 MiB | 53.37 ms | 18.74 条／秒 |
| 500 | 8.35 MiB | 303.15 ms | 3.30 条／秒 |
| 1000 | 16.69 MiB | 536.35 ms | 1.86 条／秒 |

折算值不是生产吞吐承诺。关键事实是：**成本随全部存档玩家增长，而不仅随在线人数增长；1000 名新手存档下，单次轻量操作已消耗约半秒。** 数据库与广播只会增加工作；这不适合作为长期积累玩家的中型游戏主路径。

现有 [socket-load-smoke.mjs](/Users/jar/Documents/翡翠/jade-market-prototype/scripts/socket-load-smoke.mjs:15) 明确关闭持久化，测试的是 25 个连接和一轮改名。它没有经过生产耐久协调器，不能证明上述路径具备容量。

最小修改建议：

1. 每类指令明确受影响的玩家与世界集合，只复制、验证和记录这些根；完整世界校验用于加载、检查点和审计，不在每条轻量指令上重复执行。
2. 保留周期检查点与增量日志，但让增量由受影响根生成，避免先复制整个世界再寻找变化。多玩家交易必须覆盖双方和托管集合。
3. 排行榜取有界页面或前若干名，市场和直播间按页面／订阅同步；私人状态只发给相关玩家。先缩减数据范围，无需建设消息总线。
4. 定时扫描先检查到期集合；同类 tick 已排队时合并重复调度。账号密码计算放在全服写队列之外，最终执行时重新校验身份和账号唯一性。
5. 写队列有基本长度／等待时间上限；数据库事务设置语句和锁等待超时。当前只有连接建立超时，SQL 等待没有显式期限，单条阻塞会拖住整个世界队列。

上述措施是在现有单进程内减少成本与等待，不是横向扩容。不要用每条操作多存几份完整世界、增加 Node 副本或无限重试来解决问题。

验收：带真实 PostgreSQL 和生产持久化，按实际在线目标及操作频率测指令延迟、事件循环延迟、队列长度、内存与存档规模；分别增加在线连接数和累计存档玩家数。模拟正常混合操作、同时购买同一商品、任务集中到期和数据库短暂变慢，不只测改名。累计玩家增长不应让一个无关玩家的指令成本近似线性增长。

### R9 就绪探测把读成功当成写入恢复

**需要修改；存在运维状态误报 bug。**

[数据库探测](/Users/jar/Documents/翡翠/jade-market-prototype/server/shell/postgres-world-persist.js:505) 只执行 `SELECT 1`；[健康服务](/Users/jar/Documents/翡翠/jade-market-prototype/server/observability/runtime-health.js:34) 只要该探测成功，就清除错误并重新标记 ready，即使返回的 `consecutiveFailures` 仍大于零。

复现：标记持久化写入连续失败 3 次，提供一个 SELECT 1 成功、仍报告 3 次失败的探测结果；健康服务返回 `ready=true` 且清空错误。数据库只读、写权限异常或部分存储故障等情况下，连接能读并不能证明游戏操作可写。

最小修改：区分连接探测与实际写入健康。发生写故障后，保持未就绪，直到一次受控的小写探测或正常耐久写入成功；不要每次读取健康接口都写整份世界。同步更新 `/metrics` 的 ready 指标，并增加队列等待、事件循环延迟及写失败次数这几项直接可操作的指标。

验收：数据库允许读、拒绝写时保持 503；写入能力恢复并完成成功写操作后恢复 200；指标与接口状态一致。

## 可以保留的设计

当前值得继续使用的部分包括：单区单权威进程；领域服务与 Socket 指令分离；服务端随机与资产裁决；资金流水；多人交易的同步原子根保护；周期完整检查点加逐操作日志；投影与日志同事务提交；快照校验与旧版本回退；到期结算与重启恢复；状态补丁与版本重同步；生产关闭调试事件；密码派生、令牌哈希、精确来源、安全 Cookie、包大小与频率限制；数据库隔离、日志轮转、健康接口、固定镜像标签和备份／恢复脚本。

领域内原子保护与耐久提交分别覆盖业务部分失败和存储失败，不必仅因为“有两层”就删除一层。应避免它们重复复制完整世界，并明确哪一层决定提交。

不建议为此次整改增加微服务、Redis 集群、Kafka、Kubernetes、跨区多活、数据库主从或通用 Saga 框架。单机备份加一份异地备份和一次临时库恢复演练，属于基本恢复能力；不要求多站点灾备。一个区保持单权威进程，不应直接增加应用副本来扩容。

业务文件较大和部分模块使用全局装配接口，会增加维护成本，但本次不把“超过固定行数”作为必须重构的 bug。先修复已确认边界，再按自然业务职责逐步拆分矿区等复杂模块。

## 建议修改顺序

1. **身份与权限**：修复 R1、R5、R7，关闭无凭据认领和生产自动授权，真正使全部退出生效。
2. **提交与恢复**：修复 R2、R3、R4、R6，统一检查点边界、幂等范围和执行时对象获取；补充故障及重启测试。
3. **中型容量**：修复 R8，移除逐指令全世界复制／校验，减少广播数据，加入基本等待上限。继续沿用单权威进程。
4. **发布与运维**：修复 R9、R10、R11，完成真实 PostgreSQL、容器构建及备份恢复验收；更新架构文档中的实际保证范围。

不建议给这些步骤承诺未经评估的固定工期。容量调整会改变事务根选择，需要验证所有会改变双方资产或托管数据的交易路径。
