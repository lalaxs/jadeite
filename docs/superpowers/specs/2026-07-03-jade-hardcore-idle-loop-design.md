# Jade Hardcore Idle Loop Design

## 设计目的

《翡翠风云》当前应定位为硬核放置经营模拟，而不是单纯的玉石加工玩具或静态交易页。玩家的核心乐趣来自四件事：

- 在信息不完全的公盘里判断原石风险。
- 用有限资金安排加工、销售和再投资。
- 离线后仍能推进经营，上线时先收结果再做下一轮决策。
- 在无新手保护、无经济保底的压力下，靠订单、交易、直播和库存周转自救。

第一轮优化选择“硬核放置循环优先”。它先让 GDD v2.1 的机制骨架跑通，再逐步补齐 UI 文档中的 7 页经营后台。界面可以先服务循环，不做一次性大换皮。

## 当前原型基线

已有能力：

- Socket.IO 同步玩家状态、原石池、交易行、排行榜和市场战报。
- 原石生成、开窗、专家线索、点击选择开窗位置。
- 全料打磨、取件套件、成品库存、NPC 订单、交易行、收藏展示。
- 共享规则模块 `public/jade-rules.js` 支持取件分析、订单匹配和销售路线建议。
- Canvas 玉石渲染已经能表现原石、开窗和成品来源。

主要差距：

- 公盘仍接近“直接拍下”，缺少 GDD v2.1 的暗拍、代理上限、开标和 AI 买手补位。
- 加工链仍是“全料打磨 -> 取件”，没有粗加工、精加工、镶嵌的现实时间节奏。
- 离线推进没有统一摘要，玩家上线时看不到明确的离线收益和完成事件。
- 直播只是即时出售动作，不是可排程、可离线完成的销售渠道。
- 声望与消费、直播收入的强关联还没有形成。
- 经营报告缺少流水、利润、库存周转和自救建议。

## 目标状态

第一轮垂直切片完成后，玩家一次上线应能完成这个循环：

```text
上线 -> 查看离线结算 -> 看公盘清单 -> 开窗/估价 -> 设置暗拍出价或代理上限
-> 安排粗加工/精加工/镶嵌 -> 选择订单、交易行或自动直播销售
-> 查看资金、声望、库存和经营建议 -> 下线等待下一轮
```

这个循环的目标不是保证玩家赚钱，而是保证玩家理解每次决策的代价、风险和自救路径。

## 设计原则

- 现实时间统一：加工、公盘、直播、订单刷新都使用现实时间。游戏内“第 X 天”只做叙事包装。
- 离线可推进：所有等待型机制都应在玩家离线期间继续结算。手动直播除外。
- 暗拍保赌性：投标期间不显示当前最高价和是否领先，开标时一次揭晓。
- 资源压力可读：玩家可以卡住，但 UI 必须提示可尝试的自救路径。
- 服务端权威：资金、库存、公盘、加工完成、直播结算、声望变化都由服务端判定。
- 测试可加速：生产参数可按 GDD 设置为分钟级，但自动测试应通过加速配置在秒级完成。

## 阶段 1：时间与离线推进

### 功能

- 增加统一时间配置，包含真实玩法时长和测试加速时长。
- 给玩家状态增加 `lastSeenAt`、离线事件队列、经营流水和每日摘要。
- 玩家连接时执行离线结算：
  - 完成到期加工任务。
  - 结算到期公盘轮次。
  - 结算自动直播。
  - 刷新过期订单。
  - 生成“离线期间完成了什么”的摘要。
- 总览页显示离线摘要、下一次公盘时间、进行中任务和现金风险提示。

### 验收

- 玩家断线或刷新后，已到期任务会自动完成。
- 同一任务不会重复结算。
- 页面能显示离线完成数、收入、支出和重要结果。
- smoke test 不需要等待真实 5 分钟以上。

## 阶段 2：公盘暗拍 v2

### 功能

- 将当前原石池包装为公盘轮次：
  - 预告阶段：显示本轮原石清单和倒计时。
  - 投标阶段：玩家可对每块原石提交密封出价或代理上限。
  - 开标阶段：服务端一次性结算结果。
- 投标规则：
  - 保证金为底价或估价的 20%，未中标退还，中标抵扣成交价。
  - 投标阶段可修改出价，多退少补保证金。
  - 代理投标按“刚好赢”的价格成交，但不超过玩家上限。
  - 出价人数不足时，AI 买手补位，AI 出价不展示给玩家。
- UI 保留专家开窗和线索，但把“拍下”改为“提交暗标 / 设置代理上限”。
- 开标结果进入玩家消息、市场战报和经营流水。

### 验收

- 投标期间玩家看不到其他出价和领先状态。
- 开标后资金、保证金、库存和新闻一致。
- 余额不足支付尾款时，保证金没收，原石流向下一名或流拍。
- AI 买手能保证低在线人数时仍可开标。

## 阶段 3：生产链重排

### 功能

- 将“全料打磨”迁移为三段式生产链：
  - 粗加工：5 分钟，原石变为可规划的毛料或料子。
  - 精加工：15 分钟，将取件规划转为半成品。
  - 镶嵌：5 分钟，消耗外部材料，产出最终成品。
- 现有专家取件规划继续保留，作为粗加工或精加工中的核心交互。
- 每段任务记录成本、开始时间、完成时间、负责工位和产出。
- 已有旧字段兼容：
  - `polishingJobs` 可以迁移或归并到新的 `jobs`。
  - 已揭露原料和已有成品仍可继续使用，不强制清空玩家库存。

### 验收

- 玩家可以从原石推进到最终成品，中间阶段都能出售或继续加工。
- 离线期间三段任务都能完成。
- 旧玩家状态不会因字段变更丢库存。
- 订单、交易行、收藏、直播能识别新成品。

## 阶段 4：自动直播与经营反馈

### 功能

- 增加直播任务：
  - 手动模式：在线操作，操作要求高，收入上限高。
  - 自动保守：离线可用，成交概率高，收入较低。
  - 自动均衡：离线可用，收益和成交率平衡。
  - 自动激进：离线可用，收入上限高，但可能卖不出。
- 直播结算受成品价值、声望、模式、主播属性或简化主播参数影响。
- 声望增加：
  - 消费翠币按每 10,000 增加 10 声望。
  - 直播收入按每 10,000 增加 10 声望。
  - 切出高品质、完成订单、收藏展示继续增加声望。
- 经营报告先做轻量版：
  - 收入、支出、净利润。
  - 收入来源占比。
  - 当前库存价值和滞销提示。
  - 现金不足时显示自救建议。

### 验收

- 玩家可安排自动直播后离线，回来看到结算结果。
- 直播可能失败或低价成交，不保证收益。
- 消费和直播收入能推动声望增长。
- 经营报告能解释玩家为什么赚钱或亏钱。

## UI 落地策略

第一轮不强行完成 UI 文档的所有页面细节，但导航应逐步对齐 7 页结构：

- 工坊总览：显示离线摘要、核心资源、快捷入口和任务进度。
- 公盘竞拍：承载暗拍轮次、开窗、投标和开标结果。
- 加工坊：承载三段式加工和取件规划。
- 库存交易：整合当前交易行、可售库存、订单交付和收藏入口。
- 直播卖货：承载直播模式、选品和历史结算。
- 声望殿堂：承载声望等级、解锁和排行榜。
- 经营报告：承载流水、利润、库存周转和建议。

实际代码可以分阶段迁移，避免一次性重写 `public/main.js`。

## 数据与边界

- 资金流水应记录每笔收入和支出，至少包含类型、金额、时间和关联物品。
- 任务结算必须幂等，重复调用离线结算不会重复发奖或扣钱。
- 玩家可能现金为 0，这不是错误状态。UI 应显示可用订单、可卖库存、等待刷新或重开的选择。
- 保证金、尾款、直播失败和加工费用都必须进入经营报告。
- 所有新增服务端事件都应校验玩家所有权和资金是否足够。

## 测试策略

- 继续使用现有 smoke scripts，不引入重型测试框架。
- 新增或扩展测试覆盖：
  - 离线结算幂等性。
  - 公盘暗拍的保证金、AI 补位、代理上限和开标。
  - 三段式加工任务在加速时间下完成。
  - 自动直播结算和声望增长。
  - 经营流水收入、支出和净利润汇总。
- 保留渲染与规则 smoke tests，确保专家线索和 Canvas 渲染不被破坏。

## 非目标

本轮不做以下内容：

- 数据库存储和真实账号系统。
- 完整多人借款系统。
- 完整 7 页 UI 的所有弹窗、快捷键和动画。
- 真实支付、充值或外部服务。
- 复杂主播雇佣市场。
- 彻底重写前端架构。

## 接受标准

- 玩家能通过暗拍获取原石，而不是直接购买。
- 玩家能把原石推进到至少一个可出售的成品阶段。
- 玩家离线后回来能看到完成任务、销售、收入或亏损摘要。
- 玩家可以通过自动直播变现成品，并承担收益方差。
- 声望能随高品质产出、订单、消费和直播收入增长。
- 页面能说明下一步该做什么，尤其在现金紧张时给出自救路径。
- `npm test` 或对应 smoke tests 能验证核心循环不崩。
