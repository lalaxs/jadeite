# 翡翠街直播摊位设计

**日期：** 2026-07-24  
**状态：** 已确认，进入实现  
**范围：** 直播间营业、公开浏览、真人购买、AI 购买、售罄关闭和 UI 氛围表现

## 1. 目标

把现有“单件成品进入倒计时，结束后随机结算”的自动直播任务，升级为公开、持续营业、只销售成品的高级摊位。

玩家上架一组成品后开启自己的直播间。直播间会在公共直播大厅展示，其他玩家与 AI 客人都能浏览和购买。房主离线后直播间继续营业；最后一件商品售出时自动关闭。

## 2. 已确认规则

- 保留现有直播经营许可作为直播功能的解锁条件。
- 开播时必须一次上架 3–20 件成品。
- 每件成品由卖家单独设置固定售价。
- 真人玩家与 AI 客人看到并支付同一售价。
- 开播后允许补货，同时在售数量不得超过 20 件。
- 已经开播的直播间即使只剩 1–2 件商品，也继续营业。
- 卖家可以主动关闭直播间，所有未售成品立即退回库存。
- 商品售出后立即从房间移除；最后一件售出后直播间自动关闭。
- 卖家下线后继续营业，真人玩家和 AI 客人仍可购买。
- 点赞数和预设弹幕只负责营造直播氛围，不参与成交计算。
- AI 购买主要受售价/估值比例、成品品质和卖家声望影响。

## 3. 方案比较

### 方案 A：玩家持有直播间状态（采用）

每位玩家持有一个 `livestreamRoom`。公共快照把所有营业中的房间投影为直播大厅列表。

优点：

- 房间所有权、离线营业和卖家收益天然与玩家状态绑定。
- 补货、关闭、售罄和历史记录边界清晰。
- 不需要把直播语义塞进交易行挂单。
- 可复用现有多人广播、库存、账本和任务系统。

### 方案 B：给交易行挂单增加直播标签

优点是成交代码复用最多，但无法自然表达一个房间包含 3–20 件商品、统一关闭、轮播、点赞和 AI 访客节奏。直播间生命周期会散落在交易行逻辑中，因此不采用。

### 方案 C：独立全局直播间注册表

适合数据库与跨服架构，但当前原型所有持久状态都挂在玩家对象上。额外全局注册表会增加同步与恢复成本，因此暂不采用。

## 4. 数据模型

玩家新增：

```js
livestreamRoom: {
  id,
  status: "live",
  startedAt,
  lastActivityAt,
  nextAiVisitAt,
  likes,
  items: [
    {
      id,
      product,
      price,
      listedAt
    }
  ],
  sales: [
    {
      id,
      productId,
      productName,
      price,
      buyerType,
      buyerName,
      soldAt
    }
  ]
}
```

约束：

- 每位玩家最多一个营业中的直播间。
- `items` 中的成品已从普通库存移出，不能同时交订单、收藏或在交易行挂牌。
- 公共快照只暴露安全的成品信息，不泄露隐藏品质字段。
- `sales` 只保留最近记录，防止内存无限增长。

旧的 `livestreamJobs` 和自动结算函数暂时保留作兼容，不再由新直播间 UI 创建。

## 5. 服务端行为

### 5.1 开播

客户端提交 3–20 个 `{ productId, price }`。

服务端统一校验：

- 已取得直播经营许可。
- 当前没有营业中的直播间。
- 商品数量在 3–20 之间，商品 ID 不重复。
- 所有商品都属于玩家、处于成品阶段且仍在普通库存。
- 所有售价为不低于 100 的整数。

校验全部通过后才一次性把商品移入直播间，避免部分成功。

### 5.2 补货

客户端提交 1 个或多个商品与价格。服务端确保补货后的在售数量不超过 20，再一次性移入房间。

### 5.3 真人购买

购买请求包含房间 ID、商品项 ID 和请求 ID。

服务端按当前状态重新查找商品，依次校验：

- 房间仍在营业。
- 商品仍在售。
- 买家不是卖家。
- 买家现金足够。

成交后从房间移除商品、扣除买家现金、把成品放入买家成品库存，并把售价作为直播收入立即记入卖家现金和账本。若商品已被 AI 或另一玩家先买走，则返回“商品刚刚售罄”，不重复扣款。

### 5.4 AI 访问与购买

服务器周期性处理所有营业中的房间，不要求房主在线。

每次 AI 访问：

1. 增加少量点赞，表示直播间仍有流量。
2. 从在售商品中挑选一件进行购买判断。
3. 按售价/估值比例生成基础购买概率：低于估值更容易成交，高于估值越多越难成交。
4. 叠加有限的成品分数与卖家声望加成。
5. 购买成功时复用统一成交函数，买家类型记为 `ai`。
6. 设置下一次 AI 访问时间。

点赞不进入概率公式，避免表现层数值形成隐性战力。

### 5.5 关闭

- 主动关闭：全部未售商品退回卖家成品库存，房间归档。
- 自动关闭：最后一件商品成交后立即关闭，不退回商品。
- 已成交记录进入现有直播历史/任务/消息体系。

## 6. 界面设计

直播页面分为“我的直播间”和“正在直播”两个区域。

### 6.1 未开播

- 展示可上架成品列表。
- 每件商品包含缩略图、名称、估值、勾选框和售价输入框。
- 底部固定显示“已选择 X/20 件”。
- 少于 3 件时开播按钮禁用，并明确提示至少需要 3 件。

### 6.2 我的直播间

- 使用与公共房间相同的直播卡片。
- 显示直播中标识、点赞数、剩余商品数与本场成交额。
- 提供“补货”和“关闭直播”操作。
- 补货区只显示未被其他系统占用的成品。

### 6.3 公共直播大厅

每个营业中的房间显示为一张大型 UI 卡片：

- 卡片主画面循环播放当前在售成品图片。
- 主画面显示商品名称、固定售价和购买按钮。
- 顶部显示房主名称、直播中状态、点赞数和在售数量。
- 画面下方循环显示预设弹幕。
- 卖家查看自己的卡片时不显示购买按钮。
- 真人买家购买后通过服务器广播立即看到售罄和下一件商品。

轮播仅改变画面展示，不改变商品购买概率和排序。

## 7. 错误与并发处理

- 开播和补货使用全量预校验，任何一项失败都不移动库存。
- 购买由服务器单点串行处理，并使用请求 ID 防止重复提交。
- 商品售出、补货或关播后立即广播世界状态。
- UI 遇到已售罄商品时显示轻提示并刷新房间，不保留失效购买按钮。
- 卖家离线不影响房间状态、AI 访问或收益入账。

## 8. 测试范围

服务端测试：

- 少于 3 件、超过 20 件、重复商品、无许可和非法售价不能开播。
- 3 件和 20 件可正常开播，商品从库存原子移入房间。
- 补货不能超过 20 件。
- 主动关闭会完整退回未售商品。
- 真人购买扣款、转移商品并给卖家入账。
- 不能购买自己的商品。
- 重复或并发购买不会重复扣款。
- AI 可购买离线玩家商品。
- 最后一件售出后自动关闭。
- 公共快照不泄露隐藏品质字段。

前端测试：

- 页面包含开播选择、价格输入、3–20 件计数、补货和关播操作。
- 公共卡片包含轮播画面、点赞、弹幕、价格与购买按钮。
- 自己的房间不显示购买按钮。
- 移动端卡片不会横向溢出。

浏览器验证：

- 两个独立玩家打开页面，A 开播、B 浏览并购买。
- A 下线后，B 仍可购买。
- 商品售罄后双方页面都显示房间已关闭。
- 桌面和 390px 移动视口均可完成开播与购买。

## 9. 非本轮范围

- 真人点赞、真人发送弹幕。
- 直播间等级、装修、礼物、砍价和主播话术。
- 外部视频流或真实视频播放。
- 数据库存档与跨服务器直播大厅。
